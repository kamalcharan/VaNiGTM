## 1. Pulling fresh — submodules MUST be initialised

**vikunawebsite has `vanigtm/` as a git submodule.** A plain `git clone` of the parent gives you an empty `vanigtm/` directory. `npm run db:migrate` will then fail with confusing errors because the migration files aren't there. Every new checkout, and every switch between branches that changes the submodule pointer, needs one extra command:

```bash
# after clone
git clone https://github.com/kamalcharan/vikunawebsite.git
cd vikunawebsite
git submodule update --init           # NOT --recursive; see below

# after checking out a branch that carries a different submodule pointer
git submodule update --init
```

**Do NOT use `--recursive`.** VaNiGTM's `lobehub/lobehub` orphan gitlink was removed this session (commit `887ba3f`) so `--recursive` no longer fails as it used to — but there's still no reason to descend, and the safer habit is `--init` alone. If you inherit an older parent commit (pre-`6e991ab`), `--recursive` will crash with `fatal: No url found for submodule path 'vanigtm/lobehub/lobehub' in .gitmodules`.

**Windows / PowerShell** — `&&` is only a valid statement separator from PowerShell 7+. On Windows PowerShell 5.1, use `;` between commands OR run them on separate lines. And quote paths that contain spaces:

```powershell
cd "D:\projects\core projects\website\vikunawebsite-git"
# not: cd D:\projects\core projects\website\vikunawebsite-git
```

The pull sequence is worth pinning in a README:

```powershell
cd "D:\projects\core projects\website\vikunawebsite-git"
git fetch origin main
git checkout main
git pull origin main
git submodule update --init
git checkout -- vani-app/next-env.d.ts   # if it comes back dirty from dev
```

Then, from the same directory, migrations:

```powershell
cd vanigtm/backend
npm run db:migrate
```

## 2. VPS Postgres — swapped to pgvector

**The `vikuna-postgres` container was migrated from `postgres:17-alpine` to `pgvector/pgvector:pg17`** during this session. Same Postgres 17.9 major version, same `docker_pg_data` volume, zero data change. Compose file at `/opt/vikuna/docker/docker/docker-compose.yml`; backup as `docker-compose.yml.bak`.

`pgvector` extension enabled on `vani_gtm_db` (v0.8.6). Verified:

```bash
sudo docker exec vikuna-postgres psql -U vikuna_admin -d vani_gtm_db -c "SELECT extname, extversion FROM pg_extension WHERE extname='vector';"
```

**Rollback if ever needed:**
```bash
cd /opt/vikuna/docker/docker
sudo cp docker-compose.yml.bak docker-compose.yml
sudo docker compose up -d postgres
```

Same volume, same data — reverting is safe.

**One-line footgun avoided this session:** the earlier attempt was `apt-get install -y postgresql-16-pgvector` on the host, which spun up an EMPTY PG 16 host cluster on port 5433 (the real DB is Postgres 17 in Docker). That empty cluster has since been dropped (`sudo pg_dropcluster --stop 16 main`). Do NOT install host-level Postgres packages when the DB is in Docker; the fix is a container image swap, not a host install.

## 3. What each slice built

### Phase 1 — Compose path

Migration 244: three seed talent packs into `vani_domain_pack` under `domain='technology-saas'` — Backend Engineering, Frontend Engineering, Product & Design. Payload namespaced under `vara.starter` with must-haves + knockouts + threshold + suggested titles.

`POST /vara/jd/compose` runs one transaction: `vani_role_family` upsert + `vara_family_profile` if new + `vara_scoring_config` v1 (append-only) + `vara_jd` + `vara_jd_version` v1 + subscription flip `activating → live` (first publish only) + two `vani_audit_log` rows. Idempotency-in-practice via `pg_advisory_xact_lock` on `hashtext(tenant:key)` + 60s freshness check on `(tenant, family, title)`. Full cross-process store-and-replay (schema change) flagged in the header.

Frontend: `OnboardingRunner` and `JdStudio` swapped from mock to real API. `useQuery` inside `DataBoundary`. Publish uses `apiFetch` with per-attempt `Idempotency-Key` minted via `useRef`. `UX_DONE_KEY` deleted; landing subscription is server-truth. **Edit-in-place hidden with a note** — needs `POST /vara/jd/:id/version` which lands with proper JD versioning; Duplicate covers the near-neighbour case meanwhile.

Verified: E2E 20/20 (activate → doorway loads real families → prefilled from pack starter → publish → done card → doorway shows JD with v1 + Duplicate → landing flips to Live from DB).

### Prompt Store slice

Migration 245: `vani_prompt` — one table, two scopes (`system` + `tenant`), append-only content trigger, one-active-per-scope partial unique index. Constraint requires `approved_at` when `active=true` (V-11; `approved_by` stays nullable until the vn_user bridge lands). Same platform+tenant RLS pattern as `gt_tags` (migration 235): system rows readable by every tenant, tenant rows only by their tenant.

`backend/src/vani/prompt-store.ts` — `resolvePrompt(db, key)` picks tenant override else newest active system version (one SELECT with `ORDER BY (scope='tenant') DESC, version DESC`). `renderPrompt(prompt, vars)` does `{{name}}` substitution and throws `PromptVariableMissingError` on missing declared vars.

Endpoints `GET /vara/prompts`, `PATCH /vara/prompts/:key` (refuses if system doesn't exist for key, refuses if override drops declared variable, self-approves for MVP), `DELETE /vara/prompts/:key` (revert to system; history preserved).

Prompt Studio UI at `/agents/vara/prompts` — list + detail + system body (read-only) + editable override with variable-coverage validation. Save mints Idempotency-Key. Verified: E2E 16/16.

Seeded system prompt: `vara.composer.ask_next` — proof-of-shape. Real caller (Composer) still runs the scripted preview; the LLM wiring lands with Phase 2.

### Semantic Layer slice

Migration 246: `CREATE EXTENSION IF NOT EXISTS vector` (guarded — fails loud if pgvector missing). `vara_skill` (tenant-scoped canonical skill dictionary with `embedding vector(768)` + HNSW cosine). `vara_family_profile.axes_embedding vector(768)` + HNSW. `vara_candidate.profile_embedding vector(768)` + HNSW. `vara_match_log` (append-only, tenant-scoped, records every semantic-match decision).

`backend/src/vani/embed.ts` — `embedText(text) → number[768]` using `LLM_PRIMARY_URL` + `EMBED_MODEL` (default `nomic-embed-text`). Loud errors: `EMBED_UNREACHABLE`, `EMBED_HTTP_<status>`, `EMBED_BAD_SHAPE`, `EMBED_WRONG_DIM`. Helpers `toVectorLiteral()` and `canonicalizeSkill()`.

`backend/src/vani/match-log.ts` — `recordMatch(db, input)` writes one row per decision. MUST be called BEFORE the outcome commits (audit invariant).

`docs/db/pgvector-install.md` — apt/Windows/macOS install steps, verify commands, model note (nomic-embed-text 768-dim on Ollama).

**Nothing wired to a runtime writer yet.** The tables are empty and the helpers are imported by nothing. First real caller is Phase 2's Extractor. That was the "invisible infrastructure" slice — labelled as such at push time so no one wonders why nothing changed in the app.

## 4. Deferred, named so the next session doesn't rediscover

- **`vn_users` ↔ `vani_user(id)` bridge.** JWT carries a `vn_users.id`; several columns (`vara_jd.created_by`, `vara_jd_version.created_by`, `vani_prompt.approved_by`) reference `vani_user(id)`. Currently write `null`. Audit spine's `actor_id` names who did it (bare uuid, no FK). A small bridge (upsert a `vani_user` per `vn_users` on first touch) lets those NOT NULL constraints tighten.
- **`vani_idempotency` store.** Cross-process store-and-replay for `POST /vara/jd/compose`. Advisory-lock idempotency covers the in-session cases; a hard refresh mid-flight can create a duplicate JD.
- **Body-hash dedup on `PATCH /vara/prompts/:key`.** A re-save with identical body still creates a new version row. Safe (append-only stays honest), cosmetically noisy.
- **Ollama `nomic-embed-text` model** — pull on the LLM host before Phase 2 (`ollama pull nomic-embed-text`).
- **Rotate 4 exposed keys** — `ANTHROPIC_API_KEY`, `JWT_SECRET`, `LLM_PRIMARY_KEY`, `DB_PRIMARY` password. Outstanding since the 2026-08-17 handover.
- **BYOK LLM encryption** (`vani_llm_provider.credentials_enc`) — gates Phase 2 for tenants that BYOK.
- **LLM path stability on VPS** — vocabulary step still fails; blocks Phases 2, 5, 6.
- **MSG91 adapter port** — gates Phase 5 candidate comms.
- **The worker is not running on the VPS** — carried from 2026-08-17 handover, still true. `agent-core/worker.ts` says "Separate process"; `docker-compose.vani.yml` defines only `vani-backend`. Anything event-driven is dead on that box until the worker becomes a compose service (~400MB).
- **Event queue has no stale-row reclaim** — `agent-core/event.store.ts`. Real bug; a worker that dies mid-run orphans its in-flight events permanently. Blocks any UI that awaits event completion.

## 7. Working method that held up this session

Two disciplines that were the difference between clean landings and the earlier session's rework:

1. **No code without an explicit "go".** Every slice was: propose scope + shape → wait for OK → build → verify → commit. Charan pushed back on the compose migration's SQL syntax; the fix was clean because the shape was agreed first.
2. **Schema changes named as schema changes.** The August 17 POA said "no schema changes." The prompt store and semantic layer both needed schema. Both went to Charan as explicit requests with the shape drawn (columns, constraints, indices) BEFORE the migration was written. Both approved. The POA now reflects reality.

Keep both. The next session will save time.

## 9. What NOT to do

- Do NOT skip fixture-set discipline on Phase 2 — an extractor whose prompt drifts silently is the failure mode `--comment=NO_SILENT_FALLBACKS` exists to prevent.
- Do NOT rebase `main` on either repo — always merge (both mains have merge commits already from PR flows).
- Do NOT amend a pushed commit on the shared branches — new commit on top instead.
