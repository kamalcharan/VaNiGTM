Section 1

Positioning & invariants

VaNi Platform is the tenant-facing foundation of the Org OS direction: the layer that holds an organisation's identity, people, structure and shared services, on which individually-priced agents (Vara, Nova, and those after them) are activated. It is the concrete first slice of the invariant core — core auth, core orchestration, knowledge building — that was settled as the product boundary: only the data changes per customer; this layer does not.

InvariantWhat it means in the build
Agents extend, never modifyPlatform tables never grow agent-specific columns. An agent ships as its own prefixed tables hanging off platform keys, plus declarations into the platform's registries. Activating an agent adds rows; deactivating removes them; the organisation is untouched either way.
One declaration, N projectionsA tenant states each fact about itself once — industry, people, families, provider — at the platform. Every agent receives a delegation and activates its own slice. No agent ever re-asks a platform question.
Vikuna is tenant #1vikuna.io runs as a real tenant row through the same provisioning, gates and metering as any subscriber. A behaviour that only works for the home tenant is a bug.
Shared services are the platform's voiceComms (MSG91, sender “vani”), metering, audit and embed tokens are platform services with per-agent accounting. Agents call them; they never re-implement them.
The audit spine is singularOne vani_audit_log across all agents. “What happened to this entity” is answerable from one table, with actor_type ∈ human | rule | timer | system — “model” is never a legal actor, platform-wide.
Per-agent commerceEvery agent carries its own commercial gateway and metering units, per the family's pricing model. The platform aggregates; it does not bundle.
Section 2

Personas

The platform has four personas — and one of them is not human. Treating the agent as a persona is what makes the integration contract (Section 3) a first-class product surface rather than tribal knowledge.

O1 · OPERATOR

Vikuna platform team

Runs VaNi as a product across tenants and agents.

Provisions and suspends tenants, registers agents, authors and publishes domain packs, watches fleet health and the commercial gateway.

Cares about: tenant isolation, unit economics, one platform serving every agent.
O2 · TENANT ADMIN

The organisation's owner-operator

Completes the platform lane once; owns org-level state forever.

Declares the org profile and industry binding, manages domains, users, memberships, role families, per-agent role assignments and the LLM provider.

Cares about: declaring things once, controlling who can act where, no surprises on the invoice.
O3 · AGENT

Vara, Nova, and successors

A software persona with a contract, not a privileged insider.

Registers into the fabric, declares its roles and metering units, consumes identity/context/services through the contract, and extends the org through its own prefixed tables.

Cares about: a stable contract, everything it needs available at activation, nothing platform-side to build.
O4 · MEMBER

The tenant's people

One identity, many agent roles.

Logs in once (bridged auth), holds platform membership, and acts inside each agent only through the roles granted per agent — an HM in Vara, nothing in Nova.

Cares about: one login, seeing only what their roles allow, their actions being attributed correctly.
Section 3

The agent integration contract

The centerpiece. Any agent — Vara today, Nova next, an O2C agent later — plugs into the platform through exactly this contract. If a capability is not in the contract, the agent builds it in its own prefix or requests a platform change; it never reaches into vani_ directly.

An agent MUST DECLARE (writes into platform registries, at registration)

DeclarationWhere · example (Vara)
Identity & versionvani_agent — code vara, name, version. One row per agent, platform-wide.
Role catalogvani_agent_role — ta, hm, calibration_approver. The tenant assigns people to these; the agent only reads assignments.
Metering unit typesRegistered with the gateway — candidate_scored, knockout_close. Every unit the agent will ever bill must be declared before first emission.
Template setvani_template codes + channels the agent sends with — Vara's six (ACK-01 … POOL-02). Instantiated per tenant at activation.
Pack namespaceThe key under which the agent reads vani_domain_pack.payload — e.g. payload.vara (question banks, knockout templates, signal adapters).
Activation checklistThe agent's own readiness gate items, machine-checkable, evaluated by the platform's activation flow (Flow F1).

An agent MUST CONSUME (reads/calls, never re-implements)

CapabilityContract
Identity & membershipUsers come from vani_user/vani_membership; authorisation inside the agent comes from vani_user_agent_role. never an agent-local user table.
Org contextvani_role_family read-only; agent-specific behaviour hangs on a 1:1 extension row in the agent's prefix (the vara_family_profile pattern).
Pack bindingvani_tenant_pack_binding is the tenant's single industry declaration; the agent activates its namespace, asks nothing again.
LLM providerPer-tenant credentials via vani_llm_provider. never pooled, never agent-stored.
CommsSends only via the platform comms service (MSG91, sender “vani”) referencing declared template codes; every send lands in vani_comms_log.
MeteringEmits vani_metering_event rows (agent = self) at the declared unit moments — ideally from triggers, as Vara does at snapshot time.
AuditEvery state change writes vani_audit_log in the same transaction, actor_type from the legal set, payloads id-referencing (no PII).
Embed tokensPublic surfaces are served under vani_tenant_domain entries through the platform's origin-bound token service (Flow F3).

An agent MUST NEVER

alter vani_ tables store users or credentials send comms around the platform service read another agent's prefix touch another tenant's rows use “model” as an audit actor — the first and last are enforced in the database; the rest by code review against this contract.

The test of the contract: Nova's activation should require zero platform DDL — a vani_agent row, its role catalog, its unit types, its template set, its pack namespace, and its own nova_ tables. If Nova needs more than that, the gap is a platform change request, not a workaround.
Section 4

Shared services

ServiceSpecification
Identity & tenancyTenant records, domains with verification, users with auth_ref bridging the existing auth stack (Supabase or successor — authentication stays where it is; the platform owns identity, not login). Memberships carry platform roles; agent roles are separate and per-agent.
Agent fabricRegistry of agents and their role catalogs; subscriptions per tenant with lifecycle provisioned → activating → live → suspended. Deactivation deletes agent-prefix rows and role assignments; org state survives untouched.
Org contextRole families as an agent-neutral graph (with hierarchy). The platform guarantees stability of family ids so agent extension rows never dangle; family deletion is blocked while any agent extension references it.
Domain packsPlatform-authored, versioned artifacts (code + version unique) with per-agent namespaces in the payload. Publishing is append-only — a new version, never an edit. Tenants bind once; agents read their namespace at activation and on pack upgrade (explicit tenant-approved upgrade, no silent rebinding).
Comms (MSG91)One delivery infrastructure — the MSG91 integration proven in ContractNest, sender identity “vani”, tenant identity in template content. The service owns template registration, WhatsApp approval tracking, sends, provider status callbacks, opt-outs, and the append-only log. Agents pass template code + variables + recipient ref; nothing else.
Metering & gatewayAppend-only events, per agent per tenant, aggregated by the commercial gateway into per-agent statements. Guarantee: every event reconciles 1:1 with a referenced row (ref_table, ref_id) — an invoice line is always traceable to the exact snapshot or close that earned it.
Audit spineOne append-only log, agents attributed, actor rules platform-wide, payloads id-referencing by policy (this is what lets DPDP purge leave audit intact). Query surface: by entity, by tenant, by agent, by actor.
Embed & tokensOrigin-bound tokens issued per tenant domain for public surfaces (candidate chat, status pages — and whatever Nova exposes later). Validation at the edge against embed_origins; rejects are audited. Tokens are scoped (tenant, agent, surface) and revocable.
LLM providerBYO per tenant: encrypted credentials, verified by test call, health-checked. Provider outage is surfaced to agents as a capability flag so each degrades by its own plan (Vara: web-form intake + queued extraction).

PE1

Tenant lifecycle

operator-owned
VN-01O1
Provision a tenant. As the operator, I create a tenant — Vikuna included — with its RLS scope, domains and data region, before any admin logs in.
vani_tenant + vani_tenant_domain rows; every later row RLS-scoped; no home-tenant special case.Wizard link issued to the named Tenant Admin.
VN-02O1

Suspension cascades to all vani_tenant_agent rows and revokes embed tokens; resume restores exact prior state.Both actions audited with actor.

PE3

Agent fabric

the contract, operationally (Flow F1)
VN-20O1
Register an agent. As the operator, I register an agent with its full declaration set — identity, roles, unit types, templates, pack namespace, activation checklist.
Registration is complete or rejected — no partially-declared agents.Nova's registration requires zero platform DDL (the contract test).

Section 7

Non-functional requirements

RequirementTarget · v1
IsolationRLS on every tenant-scoped table (validated: cross-tenant sessions are blind); per-tenant LLM credentials never pooled; agent prefixes mutually unreadable by contract.
Availability & degradationPlatform services degrade independently: comms outage queues sends with SLA alerting; LLM outage flips the capability flag; embed edge fails closed. No degradation path loses a row.
ImmutabilityAudit, comms log, metering and pack versions are append-only, database-enforced. The DPDP purge function is the single sanctioned bypass, itself audited.
Key managementLLM and provider credentials encrypted at rest; embed tokens signed, scoped and revocable; JWT secrets per deployment as per existing VaNi practice.
ObservabilityFleet view for the operator: per tenant × agent — activation state, metering run-rate, comms delivery rates, audit anomalies (e.g. edge rejects).
Scale postureSized for the family's near-term reality: tens of tenants, a handful of agents, thousands of metering events/day — with nothing in the design that caps an order of magnitude more.
Section 8

Legacy & naming

This platform layer is the concrete first slice of the VaNi Core direction settled earlier — kernel-as-dependency rather than copy-the-template — arrived at bottom-up: Vara needed the spine, so the spine got built first. Legacy VN_ and GTM tables coexist untouched; existing auth stays where it is, bridged by vani_user.auth_ref; nothing is renamed or migrated (“let history be history”). The open naming question (VaNi Core v0.1 vs VaNiBase v3.0) remains open — this document calls the layer simply VaNi Platform and is compatible with either answer.

Deliberately out of scope · v1: platform-level workflow/orchestration engine (agents orchestrate themselves for now — the org orchestration agent is a later phase of the Org OS roadmap) · cross-agent knowledge graph / UNS (roadmapped after knowledge maturity) · self-serve public tenant signup (operator-provisioned in v1) · billing execution (the gateway produces statements; payment collection is external).
Section 9

Schema reference & next step

The platform schema — 16 vani_ tables across identity, fabric, org context and shared services — is fully specified, DDL'd and validated on PostgreSQL 16 in the Vara Data Model v1.0 document (migration 001_vani_platform.sql). It is not repeated here; that file is the single source of truth for structure.

Next step on go-ahead: the build plan across both documents — migration execution in VaNiGTM (001 → 003), the platform service seams as code modules (comms adapter over MSG91, token service, gateway aggregation), then Vara's skills against the contract. One Claude Code hand-off brief covers the sequence.
