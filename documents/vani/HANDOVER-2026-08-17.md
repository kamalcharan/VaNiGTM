## 5. Localhost — explicitly requested for the next session

Deferred today by decision (see `vani-app/CLAUDE.md` §0). Picking it back up:

**The mode that works** is local backend + VPS Postgres, and it needs no
production change:

```
# vani-app/.env.local
NEXT_PUBLIC_API_ORIGIN=http://localhost:3002
```
```
cd vanigtm && git checkout main && cd backend && npm install && npm run dev
```

Backend `.env` must have `PORT=3002`, `CORS_ORIGIN=http://localhost:3000`,
`NODE_ENV=development`, `DB_PRIMARY` → the VPS Postgres. No Docker locally —
the backend is `tsx watch src/server.ts`; Docker is only how it runs on the VPS.

**Facts, so they are not rediscovered:**

- The variable is `NEXT_PUBLIC_API_ORIGIN`. VaNiGTM's frontend uses
  `NEXT_PUBLIC_API_URL`, which this app never reads — and the wrong name fails
  **silently** into the mock transport.
- SameSite is about the **domain, not the port**. `localhost:3000` ↔
  `localhost:3002` is same-site, so the `sameSite:'strict'` refresh cookie is
  sent. `NODE_ENV=development` drops `secure`. Auth genuinely works.
- `localhost` → `api.vikuna.io` is cross-site: the cookie is neither sent nor
  storable over http, and `localhost` is not in nginx's
  `map $http_origin $cors_origin` allowlist (which defaults to `""`).

**The unresolved bit.** A previous attempt reached: `/health` ok, VPS Postgres
at 129ms, and `OPTIONS /api/v1/auth/login` returning **204 with
`Access-Control-Allow-Origin: http://localhost:3000`** — and the browser still
failed the login `fetch` at the network layer (`api-client.ts:151`, thrown only
when `fetch` itself throws). Ruled out: backend down, CORS refused, CSP (there
is none; `next.config.ts` sets only `reactStrictMode`).

**Next diagnostic, not yet done:** open DevTools → Network, retry the login,
read the failed request's label. `ERR_CONNECTION_REFUSED` and a CORS block look
identical in the UI and are unambiguous there. Also confirm the port Next
actually bound — if 3000 was busy it silently uses 3001, and `CORS_ORIGIN` is a
single exact-match string.

## 10. The database channel — corrected, and now a small named ask

Both this document and the repo `CLAUDE.md` state that `gtm-postgres` "has never
once connected from inside a Claude session" and that `GTM_MCP_BASIC` is unset.
**That is out of date. The channel connects.** It answered live SQL in the later
2026-08-17 session.

It still cannot answer §4's question, for a different and much narrower reason:

| | |
|---|---|
| Connects to | **`kaala_dristi_db`** |
| As user | **`kd_readonly`** |
| Needed | **`vani_gtm_db`** |
| `vani_gtm_db` exists on that server? | **Yes** — listed in `pg_database` |
| Cross-database hop possible? | **No** — installed extensions are only `pgcrypto`, `plpgsql`, `uuid-ossp`. No `dblink`, no `postgres_fdw` |

`.mcp.json` points at `https://mcp-db.dristiq.com/sse`, which is a fixed
connection; Postgres cannot cross databases without an FDW, so no query from
this endpoint can reach the `vani_` spine. **`\dt vani_*` is not answerable from
a Claude session today, but the gap is one credential wide, not a wall.**

**The ask:** an SSE endpoint (or basic-auth credential) bound to `vani_gtm_db`,
read-only. With that, §4, §3's migration-drift check and the `⚠ modified`
checksum question in §6 all become one-query jobs instead of round-trips through
Charan.

**Caution against a wrong shortcut.** Querying `vani_%` on the current channel
returns exactly one row, `vani_observation_cache` — a DristiQ table in
`kaala_dristi_db`. It is **not** evidence about the spine, and it is easy to
misread as "the spine was never applied". Check `current_database()` before
believing any `vani_`-prefixed result.
