## 5. Localhost — SOLVED. The bug was the port.

> **RESOLVED 2026-08-17 (later session).** Login, session and the whole console
> were driven end-to-end in a real headless Chromium against a local backend.
> The root cause was a **one-line documentation error that this file,
> `vani-app/CLAUDE.md` and `vani-app/.env.example` all repeated.**

### The bug

`vani-app`'s dev server binds **port 3100** — `"dev": "next dev --port 3100"`,
which it has done since the first commit of its `package.json`. `README.md` says
so correctly.

Every other document said to set the backend's `CORS_ORIGIN=http://localhost:3000`.

VaNiGTM does `origin: process.env.CORS_ORIGIN || 'http://localhost:3000'`
(`backend/src/server.ts:25`) — an **exact string match**. So the browser's real
origin (`:3100`) never matched the allowed origin (`:3000`), the browser blocked
the response, and `fetch` rejected — surfacing at `api-client.ts:151`, which
throws only when `fetch` itself throws. Exactly the reported symptom.

**The fix is one character: `CORS_ORIGIN=http://localhost:3100`.**

### Why it looked ruled out — the trap worth remembering

The old §5 recorded `OPTIONS /api/v1/auth/login` returning *"204 with
`Access-Control-Allow-Origin: http://localhost:3000`"* and concluded CORS was
fine. It was not. Reproduced here with `CORS_ORIGIN` deliberately set to `:3000`:

```
$ curl -i -X OPTIONS -H 'Origin: http://localhost:3000' … /auth/login
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://localhost:3000     ← looks perfect
```

Express `cors` with a **string** origin always answers 204 and echoes the
**configured** value — never the caller's. A hand-rolled curl that supplies
`Origin: http://localhost:3000` therefore *always* looks like a pass, whatever
the browser experiences. The browser sends `Origin: http://localhost:3100`, gets
`Access-Control-Allow-Origin: http://localhost:3000` back, sees a mismatch, and
blocks.

**So "204 + an ACAO header present" is not evidence of anything.** Compare the
ACAO value against the origin the *browser* actually sends. Curl with the real
origin, or read it in DevTools.

### The mode that actually works from a Claude web session

**Not** "local backend + VPS Postgres" — that is impossible here. **Outbound TCP
5432 is blocked** by the environment's network policy (verified: the connection
is refused, and `curl` to `vani.vikuna.io` gets a 403 at the CONNECT stage). The
VPS Postgres cannot be reached from a web session at all.

What works is a **fully local stack**, and it needs nothing off-box. Verified
working, start to finish:

```bash

pg_ctlcluster 16 main start
su postgres -c "psql -c \"CREATE USER vikuna_admin WITH PASSWORD 'localdev' SUPERUSER;\""
su postgres -c "psql -c 'CREATE DATABASE vani_gtm_db OWNER vikuna_admin;'"

# 2. Backend — the submodule gitlink is stale, so fetch main first (see §9)
cd vanigtm && git fetch --depth 50 origin main && git checkout origin/main
cd backend && npm install
#    write backend/.env — it is gitignored:
#      DB_PRIMARY=postgresql://vikuna_admin:localdev@127.0.0.1:5432/vani_gtm_db
#      DB_PRIMARY_SSL=false
#      JWT_SECRET=<any dev string>
#      PORT=3002
#      CORS_ORIGIN=http://localhost:3100      ← 3100, NOT 3000
#      NODE_ENV=development
npm run db:migrate     # 133 migrations, all applied clean
SEED_ADMIN_EMAIL=dev@localhost SEED_ADMIN_PASS='LocalDev2026!' npm run db:seed
npm run dev            # tsx watch; "API running on port 3002"

# 3. Frontend
cd ../../vani-app && npm install
echo 'NEXT_PUBLIC_API_ORIGIN=http://localhost:3002' > .env.local

```

Confirmed working: `/health` → `{"db":{"ok":true,"latency_ms":1}}`; login 200
with `Access-Control-Allow-Origin: http://localhost:3100`; the refresh cookie
lands as `pk_refresh_token` — `HttpOnly; SameSite=Strict`, **no `Secure`**, path
`/api/v1/auth` — so it persists over plain http, as predicted. In-browser the
app reaches `/dashboard` and `/smart-profile` renders all eight sections with
live 200s on `/onboarding/status?lane=vani`, `/auth/team`, `/profile/clusters`
and `/vani/competitors`.

**`NEXT_PUBLIC_*` is inlined at server start.** Writing `.env.local` while
`next dev` is already running does not switch the app off the mock transport —
restart it. Verify by grepping a served chunk for `localhost:3002`.

### Facts that survive from the old §5, still true

- The variable is `NEXT_PUBLIC_API_ORIGIN`. VaNiGTM's frontend uses
  `NEXT_PUBLIC_API_URL`, which this app never reads — the wrong name fails
  **silently** into the mock transport.
- SameSite is about the **domain, not the port**, so `:3100` ↔ `:3002` is
  same-site and `NODE_ENV=development` drops `secure`. Auth genuinely works.
- `localhost` → `api.vikuna.io` is cross-site: the cookie is neither sent nor
  storable over http, and `localhost` is not in nginx's
  `map $http_origin $cors_origin` allowlist (which defaults to `""`).

## 10. The database channel — corrected, and now a small named ask

Both this document and the repo `CLAUDE.md` state that `gtm-postgres` "has never
once connected from inside a Claude session" and that `GTM_MCP_BASIC` is unset.
**That is out of date. The channel connects.** It answered live SQL in the later

It still cannot answer §4's question, for a different and much narrower reason:

| | |
|---|---|
| Connects to | **`kaala_dristi_db`** |
| As user | **`kd_readonly`** |
| Needed | **`vani_gtm_db`** |
| `vani_gtm_db` exists on that server? | **Yes** — listed in `pg_database` |
| Cross-database hop possible? | **No** — installed extensions are only `pgcrypto`, `plpgsql`, `uuid-ossp`. No `dblink`, no `postgres_fdw` |

`.mcp.json` points at `https://mcp-db.dristiq.com/sse`, which is a fixed
connection; Postgres cannot cross databases without an FDW, so no query from
this endpoint can reach the `vani_` spine. **`\dt vani_*` is not answerable from

**The ask:** an SSE endpoint (or basic-auth credential) bound to `vani_gtm_db`,
read-only. With that, §4, §3's migration-drift check and the `⚠ modified`
checksum question in §6 all become one-query jobs instead of round-trips through
Charan.

**Caution against a wrong shortcut.** Querying `vani_%` on the current channel
returns exactly one row, `vani_observation_cache` — a DristiQ table in
`kaala_dristi_db`. It is **not** evidence about the spine, and it is easy to
misread as "the spine was never applied". Check `current_database()` before
believing any `vani_`-prefixed result.



## 11. NEW BUG — a reload on `/onboarding` logs the tenant out

Found while verifying localhost in a real browser. Reproducible, and it is in the
code, not the local setup — **production has it too.**

**Symptom.** Log in, land on `/onboarding`, press reload → bounced to `/login`,
session gone. Three runs, same context each time:

| Case | Result |
|---|---|
| Log in, then navigate to `/onboarding` | survives |
| Log in, settle 8s on `/dashboard`, then `/onboarding` | survives |
| Log in, open `/onboarding`, **reload** | **bounced to `/login`** |

**Cause.** Two `/auth/refresh` calls race on mount — in every run one returns
200 and the other 401. `refreshSession` (VaNiGTM
`backend/src/auth/token.service.ts:191`) **rotates unconditionally**: it marks
the presented token `is_active = false, revoked_reason = 'rotated'` and issues a
new one. There is no reuse grace window, and the client has no single-flight
guard — `silentRefresh()` runs on every app mount, and `_retried` in
`api-client.ts` only prevents a retry *loop*, not concurrent refreshes. So the
loser of the race presents an already-revoked token and gets a hard 401. On a
reload both in-flight refreshes can carry the stale cookie, both 401, and the
session is lost.

**Fix — one side is enough, both is better.** Give `silentRefresh()` a
module-level in-flight promise so concurrent callers await one request (client,
`api-client.ts`); and/or allow a few seconds' reuse of a just-rotated token
server-side, returning the same new pair. Note it needs an
`Idempotency-Key`-shaped answer, not a retry: retrying a rotation is what
destroys the session.

This is the "race conditions" hazard `vani-app/CLAUDE.md` warns about, showing up
for real. Worth fixing before more onboarding work, since `/onboarding` is the
surface being built and reload-during-development hits it constantly.
